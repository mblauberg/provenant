# Provenant v1.0.0

**Date:** Unreleased

Provenant is a command-line harness for running coding agents as bounded work
lanes. Each lane has an explicit access mode, a route that picks the model, and
a recorded result. Provenant also carries messages and tasks between agents,
tracks provider quota, and delivers a writer's changes to a remote branch with
the host's own Git credentials.

This is the first release. It ships as one Rust binary, `provenant`, together
with an optional macOS menu bar app and a set of skills and hook handlers that
it installs into agent clients.

## Who it is for

Provenant is a single-user tool for a developer who runs several coding agents
in parallel and wants four things: isolated worktrees, predictable model
selection, quota awareness, and a reviewable path from an agent's work back to
a branch. It is macOS-first. It is not a hosted service and has no team model.

## What it does

### Confined lanes

- `provenant dispatch` starts a provider lane from a prompt or from a manifest
  of up to eight concurrent lanes. A caller-chosen `--operation-id` makes
  retries idempotent.
- Lanes are read-only by default. `--mode worktree-write` gives a lane one
  named worktree. Extra read and write roots, network access and named
  capabilities are granted explicitly. Network is off for read-only lanes and
  on for writers unless set otherwise.
- Every lane runs under a macOS Seatbelt profile built from its access plan.
  Credential directories such as `~/.ssh` and `~/.aws` are always denied.
- No lane writes the host's shared Cargo, npm or pnpm stores. Writers get
  private toolchain caches, which start cold. Read-only lanes build offline
  from the shared Cargo registry, linked read-only.
- Claude Code, Codex, Cursor, Agy and OpenCode adapters are all enabled.
- `lanes`, `output`, `cancel`, `resume` and `reconcile` list, read, stop,
  continue and settle runs. Provider output and terminal state are kept in run
  files.
- A writer can have the host push its final head to a branch and, once the
  pushed head is verified, open a pull request.

### Fabric, across hosts

- Fabric carries messages, shared tasks and task graphs, an activity log,
  claims on issues, paths and worktrees, and fenced landings to a shared
  reference. The same tools are served over MCP (`fabric mcp`), so agent
  clients can use them directly.
- `dispatch --host` runs a lane on a configured peer host. A peer writer names
  its branch and base; the peer creates the worktree and delivers with its own
  Git credentials. Peers are reached over bounded SSH calls, and each host
  keeps its own provider sign-ins.
- `workflow session handoff` moves a chair or task session to a fresh Claude
  session on a peer. The peer receives a generated prompt (the checkpoint,
  each branch and its pushed commit, the lanes still running, and any notes),
  recreates the worktrees from origin and opens Terminal under the chosen
  account. `--dry-run` shows the prompt and plan without sending anything.
  A host accepts hand-offs only after
  `provenant config set fabric.accept_handoff true`; it is off by default.

### Accounts, quota and routing

- `accounts register` records provider accounts with a label, adapter, config
  directory, plan and priority. `quota show` and `quota tick` read and refresh
  each account's quota windows, which feed route eligibility and dispatch
  admission.
- `chair switch` checkpoints the chair and continues under another registered
  Claude account.
- Named route pools choose among eligible models by weight and provider
  pacing. `dispatch` also takes an exact `--model`, `--effort`, fallback
  models, and flags for confidential-safe and free-tier routes.
- Configuration is one typed TOML file, `config.toml`, edited with
  `config show`, `config set` and `config unset`. The `balanced`, `economy`
  and `rigorous` profiles set the defaults.

### Telemetry

- `telemetry stats` summarises local attempts, token usage and cost.
  `--usage` counts CLI verbs and Fabric tools on this host. Arguments, prompts
  and results are never recorded.
- `telemetry trace` writes attempts as Chrome Trace Event JSON for
  ui.perfetto.dev or `chrome://tracing`, with no collector needed.

### Worktrees, workflow and checks

- `worktree create`, `list` and `remove` manage isolated worktrees for
  concurrent lanes. `remove` can clear every merged one.
- `workflow` checks reviews against a receipt's risk tier and keeps delivery
  receipts and session checkpoints.
- `bench` mines benchmark tasks from merge commits, verifies them and replays
  them against routes.
- `check` runs fast repository checks.

### Install, skills and hooks

- `install` places a staged release into Claude Code, Codex, Cursor, Agy and
  OpenCode. It registers Fabric MCP and each client's files, supports
  `--dry-run`, and is verified with `check install`. `uninstall` removes it.
- The release carries 25 skills (scope, implement, deliver, code-review,
  diagnose, orchestrate and others) and the harness constitution,
  `HARNESS.md`, which sets review pressure by risk tier.
- Hooks are off unless installed with `--hooks`. Handlers exist for Claude Code
  events and for a Git pre-push guard.

### Menu bar app

An optional macOS 14+ app shows account quota (the highest-used account,
per-window bars, reset times and credits) and the lanes that need attention.
It reads everything through `provenant quota`, never touches credentials or the
Keychain, and lets you rename, reorder and hide accounts and choose the figure
shown in the menu bar.

## Platforms

- **macOS** is the supported platform for the whole harness. Confined dispatch
  needs Seatbelt and refuses on other systems.
- **Linux:** the workspace builds and its tests pass in CI, but dispatch is not
  supported.
- Building needs Rust 1.99.1, pinned in `tools/front-door/rust-toolchain.toml`.
  The menu bar app needs the Swift toolchain.
- Each provider's CLI must be installed and signed in. Lanes use that
  provider's quota.
- Peer hosts need `provenant` on the non-interactive SSH `PATH`.

## Install

There are no prebuilt binaries. Build and package a release from a checkout,
preview the install, then apply it:

```sh
cd tools/front-door
cargo build --release --locked --bin provenant
cargo run --release --locked --example package-release -- --out "$RELEASE"
"$RELEASE/bin/provenant" install --source "$RELEASE" --harness claude --dry-run
```

Close each client before applying the install. State lives under
`~/.local/share/provenant/v1` unless `--state-dir` or `PROVENANT_STATE_DIR`
says otherwise. Full steps are in the
[install runbook](../runbooks/install.md).

A first read-only lane:

```sh
provenant route list
provenant quota show
printf '%s\n' 'Summarise this repository in three bullets.' |
  provenant dispatch --operation-id demo-1 --prompt-stdin --route junior
provenant lanes --all
```

## Stability

Within 1.x, these change only by addition:

- command names, flags and `--json` output fields;
- `config.toml` keys under `schema_version = 1`;
- the state layout under `~/.local/share/provenant/v1`;
- Fabric MCP tool names and input schemas.

Removing or renaming any of them waits for 2.0. Route pools and the model
catalogue, telemetry price tables, hidden commands, skill prose, the menu bar
app's appearance and the internal crate APIs can change in any release.

## Known limitations

- Single user only, with no access control between users and no hosted mode.
- Install is from source and takes several steps.
- Confinement and quota readers depend on provider CLIs and their output
  formats, which can change without notice.
- Hook handlers cover only Claude Code and Git pre-push.
- `hosts doctor` checks Claude sign-in only.
- The menu bar app is macOS-only and starts from a LaunchAgent you install.
