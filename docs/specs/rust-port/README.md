# Whole-project Rust port

Status: proposed, 2026-10-23. The user has decided to replace Provenant's
Python and TypeScript implementation with Rust. This plan sets the crate
boundaries and delivery method; [ADR 0028](../../adr/0028-rust-port-dependencies.md)
records the landing method and dependency allowlist. It does not change an
external contract.
GitHub owns assignments and delivery state. This directory owns port rules,
the derived work breakdown and compatibility decisions.

Read [PORTING.md](PORTING.md) before taking a unit. The
[cut-over slices and prune list](SLICES.md) map commands, callers, reusable
Rust, deletion scope and judge gaps under rulebook version 6. The
[work graph](graph.json) and [source inventory](inventory.md) are generated by
[derive_graph.py](derive_graph.py). The inventory includes every tracked
Python and TypeScript source over 200 physical lines, including tests,
templates and extensionless Python entry points. It does not infer that an
unimported executable is dead.

## Preserve the observable boundary

Redesign the implementation freely inside this boundary. The current Rust
front door, rather than the retired Python stub's accidental differences,
owns the accepted [ADR 0027](../../adr/0027-rust-front-door.md) behaviour.
Its D1–D3 divergences remain intentional. For commands still delegated, the
pinned old Python/TypeScript implementation is the oracle. Record exact
oracle revision, binary digest, configuration digest and judge revision in
each comparison. Never compare two installations whose roots resolve to the
same changing worktree.

| Surface | Required compatibility | Judge |
|---|---|---|
| CLI | Verbs, aliases, flags, positional arguments, repeated and unknown flags, defaults, help, stdout/stderr bytes and newline placement, diagnostics, exit codes, cwd, argv, environment forwarding, exec and signal behaviour | J1; existing front-door parity; lane conformance |
| Records | Existing paths and names, schema/version tags, required/optional/null fields, enum values, timestamps, units, JSONL framing, digest input bytes, sidecars, atomic publication order, lock ownership and refusal behaviour | J2; differential files; lane conformance |
| Configuration | Product/instance/user files, JSON/JSONC/YAML input semantics, precedence and merging, unknown keys, defaults, refusal diagnostics, managed-file identity and reconciliation; preserve unowned data on write | J1 and J2; isolated install fixtures |
| Fabric | MCP initialisation and framing, tool names and advertised schemas, inputs, content blocks, errors, wait limits and cancellation; CLI surface, SQLite schema, migrations, transactions, claims, sessions and landing fences | J3 plus J2; database and concurrent-process differential fixtures |
| Harness entry points | Existing paths called by other harnesses, arguments, stdin, cwd, stdout/stderr, exit and environment semantics, including direct skill script invocation | J1 entry-point catalogue; independent caller fixtures |
| Environment | Names, defaults, precedence, empty versus absent values, accepted/ignored values, scope and forwarding/redaction rules | J1 environment matrix; J2 redacted launch records |
| Filesystem/process effects | Custody, one writer, no-replace terminal publication, confinement, cancellation scope, descendant cleanup and live-provider sparing | Lane conformance on Linux and macOS arm64 |

Freeze these surfaces by observation before implementing their replacement.
Byte equality applies to CLI output and byte-sensitive records such as
digest-bearing envelopes. Schema equality alone cannot prove those bytes.
For other JSON records, compare the schema and semantic values, including
absence versus null; preserve any ordering a caller observes. SQLite files
need logical schema/data/transaction equivalence, not page-for-page equality.
Compare timestamps, UUIDs, PIDs and absolute roots through explicit,
field-specific fixture bindings. No blanket deletion of volatile fields,
sorting of arrays or normalisation of diagnostics is allowed.

J1's catalogue must include every route in `tools/front-door/src/main.rs`,
`runtime/fabric` CLI and direct skill entry point, not just `provenant help`.
Audit shell and JavaScript wrappers too, including the architecture's
`scripts/detect.mjs` and `scripts/live*.mjs` entry points. The Python/TS graph
does not enumerate those files. Any surviving wrapper may exec Rust, but
shipping Python/TypeScript runtime ownership is not the final state.
An explicit `python3 path.py` caller cannot execute a Rust binary: migrate
that caller and prove the invocation works before removing its interpreter.
Until then, keep the compatibility shim and keep the port open.

Capture all environment reads and subprocess forwarding rules, including
`AGENT_FABRIC_*`, `AGENTS_HOME`, XDG roots, provider variables, profile knobs,
`PROVENANT_FRONT_DOOR*` and lane switches. Names and precedence are data for
J1, not a hand-maintained partial list here. In particular,
`CF_DISPATCH_IDLE_SECONDS` remains ignored and silence never becomes a kill
reason ([Fabric contract](../fabric-v2.md)). Test invalid values as well as
success. Existing secrets stay outside committed fixtures.

## Redesign and delete deliberately

Internal module structure, algorithms, caches, data structures, concurrency,
adapters and private APIs may change. Replace monkeypatch seams with typed
inputs and black-box fixtures; consolidate duplicate readers; remove timing
dependencies through ownership. Do not reproduce Python globals or the
TypeScript-to-Python subprocess bridge as permanent Rust architecture.

Retirement is evidence-led:

- [ADR 0020](../../adr/0020-retire-the-daemon-fabric.md) retired the daemon,
  wire protocol, old console, Herdr adapter and Rust review-portal supervisor.
  Do not resurrect their bootstrap or authority model.
- [ADR 0022](../../adr/0022-thin-fabric-mcp-execution-facade.md) retired the
  dedicated `fabric_batch` MCP registration and `FABRIC_LEGACY_TOOLS` opt-in.
  Preserve `fabric_dispatch` with `tasks[]`, named sessions and bounded graphs.
- The [supervisor deletion list](../harness/rust-supervisor.md#deletable-tests)
  and [test-by-test inventory](../harness/rust-supervisor-tests.md) govern S1–S4
  removals. They are conditional, not permission to delete entire mixed files.
  Keep `test_stale.py`, install drift checks, policy mapping, provider output
  semantics, batch custody and conformance until their replacements prove the
  same boundary. Keep direct-CLI liveness while that supported path exists.
- Delete the fake `CF_DISPATCH` transport seam, Python front-door fallbacks
  and TypeScript provider signalling only after their named replacement and
  judge gates pass. Migrate policy tests behind fake providers first.

The supervisor spec's split, "Python decides, Rust holds and commits", is a
transition seam. This whole-project plan eventually moves the decisions too.
Its promises about locking, WNOWAIT identity, never killing on silence or
bookkeeping failure, bounded observation and terminal publication survive.
Its lists of components remaining in Python/TS are no longer final exclusions.

Python-AST tooling is `retired`, with a deletion criterion on every graph unit
(PORTING.md R6). It stays outside the Rust port. Security checks remain in
Python CI while tracked Python sources exist; date lint is retargeted to Rust
tests through a separate unit. Retired units are excluded by `ready.py`.

## Phases and acceptance

| Phase | Work | Exit evidence |
|---|---|---|
| Judge first | J1 owns `tests/golden/`, J2 owns `schemas/`, J3 owns MCP transcript record/replay. Reuse `tests/lane_conformance/`; S2 rows are in flight. This lane builds none of them. | Each relevant judge passes on the pinned old implementation and fails on deliberate mutants, before the replacement is visible to its author. Save mutant definitions and failures. |
| Port leaves | Agree interfaces, then port dependency leaves in small units using the rulebook. Integrate accepted `feat/s2-lane-run` rather than reimplementing it. | Unit tests and relevant judges pass; principal diff-only review, assuming the implementation is wrong; dependency and divergence records regenerated. |
| Differential | Run isolated old/new commands, MCP transcripts, record readers/writers and process scenarios with identical fixture inputs. Repeat across all supported adapters and both platforms. | All mismatches classified and resolved or explicitly approved in [divergences.md](divergences.md); no unexplained output or state differences; old→new and new→old retained-state reads demonstrated. |
| Cut-over | Change installer/default execution only after the whole boundary is covered. Rehearse install and rollback of the complete Rust install on both Macs. | Exact-head CI green, install and rollback rehearsed, no unexplained divergence in the differential runs, external callers migrated, runtime Python/TS removed and required judge suites retained. |

J1–J3 completion is an input gate, not an assumption that their paths already
exist on this branch. Their owners supply the runner commands and coverage
manifests; do not invent a J3 runner path. Missing coverage blocks the affected
unit. An old implementation failing a new judge means the judge or the
boundary must be settled first. A mutant surviving a judge means that judge
is not yet adequate for the behaviour the mutant changed.

Keep black-box gates independently owned. A lane may propose a judge fix but
cannot weaken its own acceptance test. Cheap models implement well-bounded
pure units; senior models handle custody and state changes; principal models
review only the diff, contract and evidence, without the author's rationale.
Reviews follow `HARNESS.md`; the chair supplies cross-family coverage through
Fabric. Record only routes actually resolved in receipts. Mechanical mapping
belongs in deterministic scripts, never repeated model judgement.

## Landing method: continuous PRs to main

Decided 2026-10-23 ([ADR 0028](../../adr/0028-rust-port-dependencies.md)):
small continuous PRs. First the judges, then inert library crates, then gated
command ownership, then removal. Main remains usable throughout. Each PR gets
its own CI and review, and rulebook fixes reach later lanes immediately. Keep
old/new selection at command or owner boundaries only, and delete the old
owner as soon as its judges pass on the new one. Never run both owners over
the same live attempt or SQLite state.

For either method, a lane has one writer per worktree. Parallelise disjoint
crates after their interfaces are accepted. Crate manifest, workspace lockfile,
rulebook and generated graph changes have one serial integration owner.
Units within one crate run serially unless that owner assigns disjoint module
files. `leaves_first_waves` expresses dependency eligibility, not permission
to launch every node in a wave concurrently. GitHub issues own actual claims,
status and remaining user decisions; this graph has no live completion flags.

## Self-hosting and rollback

The swarm runs on Provenant. Pin an immutable stable install, source revision
and source digest outside all port worktrees for the chair, Fabric MCP,
dispatcher and provider supervision. Confirm the installed command, MCP
registration and root pointers resolve there before every wave. Pin provider
versions and configuration snapshots for comparisons. Do not update that
install or its shared dependency directory from a port lane. Rust candidates
run from explicit artefact paths with isolated instance roots and databases;
test providers are fake unless a live trial is authorised.

Before cut-over, stop admission, drain active owners, back up the live state
and prove both binaries can reopen a copy. Repoint the installer and MCP
registration only after that proof. Roll back by restoring the pinned install
and pointers, then invoking help, root, a retained-state read and a fake lane.
Do not roll back by restoring an old database over new writes. Incompatible
state migration needs a separately approved, reversible migration plan.
After source deletion, roll back by restoring the old implementation from Git
history and reinstalling it.

Timed trials are dropped (user decision, 2026-10-23); judges and differential
runs are the promotion gate. Keep the stop conditions: any healthy provider
killed, lost terminal record, weakened confinement or second live writer
stops promotion and reverts to the previous install. Investigate before
resuming. Runs against the user's live providers still need the user's
authority.

## Work graph and estimates

Regenerate from the repository root with Python's standard library only:

```sh
python3 docs/specs/rust-port/derive_graph.py --self-test
python3 docs/specs/rust-port/derive_graph.py
python3 docs/specs/rust-port/derive_graph.py --check
```

The script reads Git-tracked source without importing it. Python AST imports,
relative imports, literal dynamic loaders and conservative path references
produce `source_imports`. A comment-aware TypeScript token scan captures
imports, re-exports, literal dynamic imports and cross-language owner paths.
Adapter registry siblings and the imported production `ps.mjs` module are
included explicitly. `loader_review` lists
dynamic or ambiguous loaders needing lane inspection. Shell/JS execs,
environment selectors and callback injection remain manual boundary edges;
no static scanner can prove them absent.

Source cycles become per-module interface tasks followed by an explicit
integration gate. External dependants wait for that gate, not just one member
of the cycle. Interface tasks define private contracts, not new public core
types by default. Port units group Python AST statements and TS declaration
anchors, usually a few hundred source lines. Source spans include constants
and comments and may split a large function by behaviour. At claim time,
enumerate behaviours, check loader edges and refine a unit if it cannot be
completed in about half a lane-day. Regenerate IDs/dependants together before
claiming affected work. These are planning units, not line-for-line ports.

Estimates below are rough order of magnitude, not elapsed days. The base is
0.5 lane-day per port/integration unit and 0.25 per cyclic interface, including
targeted tests and one review/repair pass. The upper bound is 1.75 times the
base for difficult parsing, confinement and drift. Small modules may combine
under one crate owner after behaviour review. `workflow` includes receipt,
review, session, tracker and writing tools; the end state covers these too.
`cross-crate` is integration effort, not a crate. No elapsed-time claim comes
from dividing by the number of models.
